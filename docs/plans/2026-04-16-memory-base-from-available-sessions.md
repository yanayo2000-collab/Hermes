## 2. 已确认的业务模型与场景

### 2.1 业务类型
- 业务是 MCN：为海外付费社交平台导入女性用户
- 收入模式：
  - CPA：按导入女用户数量结算
  - CPS：按女用户后续收益抽成

### 2.2 目标人群与地区
- 目标用户：宝妈、女大学生、居家兼职女性、网赚型女性用户
- 重点地区：
  - 印尼
  - 墨西哥
  - 巴西
  - 以及其它印尼语 / 西语 / 葡语区域

### 2.3 核心痛点
- 广告成本波动大
- 广告易被拒登 / 封户
- WhatsApp 号码容易被封，导致线索流失
- 用户对“是否真的赚钱、是否正规、安全性”存在不信任
- 从接触到注册成功转化率不高
- 夜间注册用户进官方群仍依赖人工审批

## 3. 当前确认版业务全链路

### 3.1 投放入口
- Meta / TikTok 广告
- 用户进入：
  - 落地页
  - 或 Meta Message 里的 AI 对话

### 3.2 私域承接
- 落地页流量：进入 WhatsApp 注册群，注册后私聊人工客服
- Message 流量：在 Message 中由 AI 对话收集与引导注册

### 3.3 注册群审批
- 注册群的入群审批，当前真实业务里先由人工客服管理员处理
- 注册客服每次审批一批用户进群时，要记录：
  - 对应注册群组
  - 对应人数
- 这批次数据在 CRM 里对应独立模块：`ywruquninfo`

### 3.4 收集用户信息
- 用户手机号：来自 WhatsApp 账号
- 用户账户 ID：
  - 用户主动发数字文本 ID
  - 或发送截图，由系统/人工识别
- 注册群链路：由人工客服收集
- Message 链路：规划由 AI 收集

### 3.5 公会后台绑定
- 当前仍以人工为主
- 真正业务闸口在这里
- 只有绑定成功，才继续往下走
- 后续目标：由系统打通自动绑定

### 3.6 绑定失败分支
- 不进入 CRM
- 先和用户二次沟通
- 核对 ID 是否正确
- 若 ID 正确，再解释可能原因：
  - 已加入其他公会
  - 设备注册账号数过多

### 3.7 绑定成功分支
- 进入 CRM 入库 / 更新
- 凭证图不是主流程必需，不应阻塞 CRM 入库
- 如有凭证图，可选上传到 OSS 并回写 `fileUrl`

### 3.8 官方群流程
- 客服发送 WhatsApp 官方群链接
- 用户申请加群
- 管理员人工审批
- 审批依据：
  - 已绑定公会
  - 已入 CRM
- 后续目标：AI 审批官方群

### 3.9 后续运营
- CRM 持续记录
- timeline 可查
- funnel 可看
- 日报可汇总

## 9. 4/13~4/16 期间关于智齿 / WhatsApp 接入的结论变化

### 9.1 中间阶段曾考虑接智齿
原因：
- 担心 WhatsApp 封号频繁
- 认为智齿可能提供更成熟的 WhatsApp 承接与多号能力
- 也讨论了 AI 是否可以接入智齿、以及是否由我操控智齿内置 AI

### 9.2 后续重新决策
最新决策已经明确：
- **第一版先不接智齿**
- **第一版也不先打通真实 WhatsApp 自动接入**

原因：
- WhatsApp 风控不稳
- 第一版更适合先把“人工客服收集 -> 系统收口 -> bind -> CRM”跑顺

### 9.3 第一版最新产品边界
第一版改成：
- 落地页来的用户继续由人工客服在 WhatsApp 里承接
- 人工客服负责收集用户手机号、文本 ID 或截图
- 系统负责后半段自动化：
  - 结构化录入
  - 截图识别
  - bind 推进
  - bind success 后 CRM 入库
  - timeline / funnel / 日报 / 归因统计

## 11. 关于“人工客服统一收口入口”的最新讨论结论

### 11.1 新思路已明确
人工客服在前台继续和真实用户聊天，
然后把：
- 用户手机号
- 文本 ID 或截图
统一收口到一个固定入口，
再由系统自动推进后续：
- 识别
- bind
- CRM

### 11.2 两种收口入口候选
#### 方案 A：Lark 机器人收口（推荐）
优点：
- Hermes / Lark 已有基础
- 日志、结构化、回执、权限更稳
- 不直接碰 WhatsApp 风控

#### 方案 B：固定 WhatsApp 工作群收口
优点：
- 客服习惯变化小

缺点：
- 自动抓群消息更不稳
- 风控更重
- 结构化更难做

### 11.3 当前倾向
- 第一版推荐以 **Lark 机器人收口** 为主
- 若客服必须依赖 WhatsApp 群，可先采用：
  - `WhatsApp 群 -> 人工转发到 Lark 机器人`

### 11.4 已形成的文档设计
已写文档：
- `docs/plans/2026-04-14-lark-or-whatsapp-intake-bridge-design.md`

文档核心结论：
- 第一版前台继续人工客服 WhatsApp 接待
- 中间用 Lark 机器人做统一收口
- 后台由 Hermes + mcn-ai-automation 自动推进识别、绑定、CRM

### 11.5 当前仍未实现的收口能力
- 监听固定 Lark 会话/话题并解析客服结构化消息
- 专用 intake 接口尚未落地：
  - `POST /api/intake/manual-cs-submissions` 目前还是建议，不是已实现接口
