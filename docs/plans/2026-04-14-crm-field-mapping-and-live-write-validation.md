## 2. 真实业务字段来源规则

当前真实业务口径：
- 用户手机号：来自用户的 WhatsApp 账号
- 用户账户ID：来自用户主动报给客服/AI 的数字，或来自截图识别结果
- 所属公会：以公会后台实际选取/绑定的公会为准
- 所属应用：由业务预设，可能不同 agent 负责不同应用注册
- 主流程只要求“拿到数字文本 ID 或账户 ID 截图 -> 公会后台绑定成功 -> 入库 CRM”
- 上传截图凭证不是 CRM 入库必需条件；如果后续要上传，仍需确保与同一用户文本信息一一对应
- 今天这种“拿旧截图验证链路能力”的做法仅用于测试，不代表正式业务流程

## 6. 一个非常重要的业务发现

### 5.1 CRM 不是主校验闸口，公会后台才是
当前真实业务规则是：
- 先在平台公会后台执行绑定
- 只有公会后台绑定成功后，才进入 CRM 入库
- 如果公会后台绑定失败，就不会进入 CRM 验证环节

因此系统设计上应遵循：
- CRM 不承担“是否允许绑定”的主判断
- CRM 只承接“已绑定成功用户”的入库与后续运营字段记录
- 如果绑定失败，应进入客服二次沟通流程，而不是先设计 CRM 人工核对环节

### 5.2 当前已知绑定失败后的沟通口径
如果公会后台绑定失败，应先与用户再次沟通，确认：
- 用户提供的 ID 是否正确

如果 ID 正确，可向用户解释失败原因可能是：
- 已加入其他公会
- 设备注册账号数过多

### 5.3 用户1/用户2验证的价值
- 用户1验证了：真实 CRM 新增写入是可行的
- 用户2验证了：截图识别与 CRM 已有记录命中是可行的

但从业务主流程看，后续是否进入 CRM，应以前置的“公会后台绑定是否成功”为准。
