# MCN AI Automation MVP 上线前接线清单与联调方案

> 目标：把当前已完成的后端 MVP 骨架，推进到“可试运行”的业务接线版本。

## 1. 当前判断

当前项目已经具备：
- Lead 入库
- Event 收集
- 账号提交双入口（数字 ID / 截图）
- 识别结果回写
- 绑定结果回写
- 自动生成下一步任务
- 入群结果回写
- Lead timeline
- Funnel report
- 状态历史

新增业务约束（已确认，需纳入下一阶段实现）：
- 用户看到广告后，先申请加入对应的 WhatsApp 注册群
- 注册群由人工客服管理员手动审批，后续统一称“注册客服”
- 注册客服每次审批一批用户进群时，会在 CRM 登记一条“注册群组 + 审批人数”记录，例如 `Piso-1, 30人`
- 主播个人 CRM 入库时，也要登记其对应注册群组来源
- 注册群组来源是测算注册客服效率、广告测试组效果、投手素材效果的重要归因字段

所以现在真正卡住上线的，不是内部代码结构，而是外部系统接线。

## 2. 上线前最后 3 个接线点

### 接线点 A：公会后台绑定执行器
当前业务事实：
- 用户可能提供纯数字账号 ID
- 也可能提供账号截图
- 最终都要去平台提供的公会后台做绑定
- 当前主流程仍是“公会后台手动绑定”
- 业务闸口在公会后台，不在 CRM：只有公会后台绑定成功后，才进入 CRM 入库
- 如果公会后台绑定失败，就先回到与用户沟通核对 ID，不进入 CRM 校验环节

要明确的 3 种可能方式：

#### 方式 A1：公会后台有 API
理想情况：
- 系统直接调用公会后台 API 绑定
- 我们把 `bind_check` 从“人工回写”升级成“自动执行 + 回写”

你需要提供：
- 公会后台 API 文档
- 鉴权方式
- 请求示例
- 响应示例
- 测试账号 / 测试环境

MVP 价值：高
自动化程度：高
推荐优先级：最高

#### 方式 A2：公会后台无 API，但有固定人工岗位
最现实情况：
- 系统把待绑定任务打到一个队列
- 人工在公会后台操作
- 操作完成后，人工通过我们后端或一个简单页面回写结果

推荐实现：
- `bind_check` 任务在系统中排队
- 运营打开“待绑定任务列表”
- 手工去公会后台完成绑定
- 然后点击：成功 / 失败
- 系统自动推进到下一状态
- 只有“绑定成功”才进入 CRM 写入与官方群流程
- 如果“绑定失败”，系统不做 CRM 入库，而是进入客服二次沟通/补偿路径

当前已知失败沟通口径：
- 先确认用户提供的 ID 是否正确
- 如果 ID 正确，则向用户解释失败原因可能是：
  - 已加入其他公会
  - 设备注册账号数过多

MVP 价值：非常高
自动化程度：中
推荐优先级：最高（如果没有 API）

#### 方式 A3：公会后台无 API，但页面稳定可脚本化
中间方案：
- 通过浏览器自动化/RPA 半自动执行绑定
- 成功后再写回

风险：
- 页面结构容易变
- 登录态和验证码可能麻烦
- 维护成本高

MVP 阶段建议：
- 先不作为首选
- 只有在人工回写成本过高时再考虑

## 3. 接线点 B：官方群入群执行器
系统内部现在已经具备：
- `group_join` 任务
- `group-join-result` 回写

现在要明确的是：真正“把用户加入官方群”的动作怎么完成。

### 可能方案

#### 方式 B1：官方群平台有 API
例子：
- 某平台支持邀请入群、审批入群、自动通过

这时可做：
- 系统直接执行加群
- 成功后回写 `group_join_success`

推荐优先级：最高（如果有 API）

#### 方式 B2：官方群需要人工审批
这时建议做半自动：
- 系统自动生成“待入群用户列表”
- 人工在官方群后台审批/拉群
- 审批后点“已完成”
- 系统写回 group join result

这是非常适合 MVP 的做法，因为：
- 不要求先打通全部平台权限
- 但你已经有完整可追踪流程

#### 方式 B3：用 Lark / CRM 做中间审批台
建议做法：
- 不把审批动作本身放在聊天卡片里
- 而是在 Lark 表格/简易后台里做任务列表
- 运营在任务列表里点击：
  - 绑定成功
  - 入群成功
  - 入群失败

优点：
- 比直接在聊天里点卡片稳定
- 避免 Lark 审批卡片类错误码问题
- 更适合初期运营协同

## 4. 接线点 C：真实入口谁来调我们的后端
当前系统接口已经准备好了，但要明确谁会来调用。

### 入口 1：落地页
应接：
- `/api/leads/upsert`
- `/api/events/collect`

需要落地页提供：
- URL 参数解析
- 点击 WA / message 时上报事件
- 唯一 trace_id 生成与透传

### 入口 2：AI 对话 / message bot
应接：
- `/api/events/collect`
- `/api/account-submissions`

需要 AI 系统做到：
- 识别用户发的是数字 ID 还是截图
- 把结构化结果推送到后端

### 入口 3：WhatsApp 注册客服
应接：
- `/api/registration-groups/approval-batches`
- `/api/account-submissions`
- `/api/tasks/{task_id}/bind-check-result`
- `/api/tasks/{task_id}/group-join-result`

MVP 最现实方案：
- 由注册客服/运营使用简易后台录入或确认
- 先登记“本次审批进注册群的人数 + 对应注册群组”
- 再继续收集用户账号 ID / 截图并推进绑定
- 不强求 WhatsApp 直接自动自动回调

### 入口 4：CRM / Lark
MVP 建议：
- CRM 或 Lark 先承担“运营操作台”角色
- 用于回写绑定结果、入群结果、失败原因

## 5. 推荐的 MVP 上线形态

### 最小可运行版本（推荐）

#### 自动部分
- 广告参数进入系统
- lead 自动创建
- 接触事件自动记录
- 用户账号输入自动入库
- 数字 ID 自动走 bind 任务
- 截图自动走 recognition 任务
- bind / group join 状态自动推进
- timeline / funnel 自动可查

#### 人工部分
- 公会后台实际绑定动作
- 公会后台绑定失败后的二次沟通与 ID 核对
- 官方群实际加群/审批动作
- 截图识别失败时人工补录账号 ID

#### 为什么这是最佳 MVP
因为它满足：
- 主流程跑通
- 关键节点可追踪
- 统计可用
- 不依赖你现在未必拿得到的外部 API 权限
- 可以先上线试运行，再逐步替换人工节点

## 6. 哪些是人工 / 半自动 / 全自动

### 当前最适合人工的
- 公会后台绑定动作本身
- 官方群最终审批/拉群动作

### 当前最适合半自动的
- 截图识别后自动提取账号 ID
- 运营只确认识别结果并执行绑定
- 运营完成绑定后点一次结果回写

### 当前可直接全自动的
- lead 入库
- event 记录
- 账号输入分流
- 任务生成
- 状态推进
- timeline
- funnel 汇总
- 日报汇总

## 8. 我对当前 MVP 的最终判断

### 结论
当前最小 MVP：可以搞定。

### 但要加一句限定
它已经具备“业务可试运行”的后端主骨架，
前提是你接受以下 MVP 边界：
- 公会后台绑定先人工执行
- 官方群审批/加群先人工执行或半自动执行
- 系统负责收口、追踪、统计、推进下一步

### 这意味着什么
不是“全自动上线”，而是：
- 先上线一个可运营、可追踪、可统计、可继续替换人工节点的最小闭环
- 后面再逐步把人工绑定和人工加群替换成 API / RPA

## 9. 下一步最推荐做的事

如果你要继续推进到试运行，我建议下一步按这个顺序：

1. 做一个简易运营操作台
- 列出待绑定任务
- 列出待入群任务
- 可以一键回写成功/失败

2. 明确落地页 / AI / 客服谁调用 `/api/account-submissions`

3. 做 1 条真实测试链路
- 从 lead 创建
- 到账号提交
- 到绑定
- 到入群
- 到 timeline / funnel 验证
